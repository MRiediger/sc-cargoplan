# Decisions

Architecture decisions with their trade-offs, numbered in the order they were made.
A decision changes only through a new entry that supersedes the old one.

## D1 – .NET 10

- **Context:** The app needs a supported runtime for years; users should not hit an end-of-life runtime.
- **Decision:** Target .NET 10 (LTS, supported until November 2028).
- **Counter-argument:** .NET 8 has more existing tutorials and wider installed runtimes, which helps the small framework-dependent build.
- **Consequence:** .NET 8 support ends November 2026, so starting on it would force a migration right after release. The self-contained EXE makes the installed runtime irrelevant for most users.

## D2 – WPF for the overlay

- **Context:** The overlay must be a borderless, transparent, always-on-top window with click-through, which needs the Win32 window handle.
- **Decision:** WPF (`AllowsTransparency`, `WindowInteropHelper` for the HWND).
- **Counter-argument:** WinUI 3 is Microsoft's newer UI stack; Avalonia would run on Linux and macOS.
- **Consequence:** WinUI 3 handles transparent windows poorly, and Star Citizen runs on Windows only, so cross-platform buys nothing. WPF forces software rendering with `AllowsTransparency` and can't be trimmed; both are acceptable for a small overlay. The app project is Windows-only; Core stays `net10.0`.

## D3 – Immutable records for the domain model

- **Context:** Planner, overlay and import pass ships, stops and plans around; accidental mutation would make plans inconsistent.
- **Decision:** Domain types are `sealed record`s with `IReadOnlyList`/`IReadOnlySet` and constructor validation; changes go through `with`.
- **Counter-argument:** Mutable classes are simpler to bind in WPF and need no copies when one value changes.
- **Consequence:** Value equality makes tests short and plans comparable. Validated properties are get-only so `with` can't bypass validation. The UI needs view models instead of binding the records directly.

## D4 – Single-file EXE distribution

- **Context:** Haulers should start the overlay without installing anything.
- **Decision:** Publish a self-contained single-file EXE (~70 MB), plus a small framework-dependent EXE (~3 MB) for users who have the .NET Desktop Runtime.
- **Counter-argument:** An installer (e.g. MSIX, Velopack) would add auto-update and a Start menu entry; one framework-dependent build would be much smaller.
- **Consequence:** Downloads are large because WPF can't be trimmed. Unsigned EXEs trigger SmartScreen warnings, which the README has to explain. Auto-update is a later evaluation (T7.2).

## D5 – Planner rack sharing

- **Context:** A cargo lift refuses the whole hand-over if a foreign crate is on the platform, so mixing destinations in one rack costs the player time. With more stops than racks, mixing can't be avoided.
- **Decision:** Racks fill in rack order (Rack 1 first) in route order, one rack per stop while racks last. Only route-neighbours share a rack (1+2, never 1+3), and sharing is spread evenly: the planner minimises the stop count of the fullest rack, then the sum of squared stop counts per rack. On a tie, sharing goes to the lowest-numbered racks. Every shared rack produces a warning.
- **Counter-argument:** Packing neighbours whenever they fit would leave more racks free for later pickups. A tie-break by crate count in the shared rack (fewer crates are easier to tell apart) would help the player more than "share in the first racks".
- **Consequence:** Free racks stay together at the end of the rack order. The crate-count tie-break is deliberately left out (YAGNI) and can become a task if the first-racks rule hurts in practice.

## D6 – Splitting stops across racks

- **Context:** A stop larger than a rack, or a route that only fits with a split, used to fail although the cargo fits the ship. A split stop costs the player an extra rack to unload; a split item puts one commodity in two places.
- **Decision:** Split only if no plan without a split exists. Ranking: fewest split stops, then fewest split items, then the D5 criteria. The planner cuts the route as one row of crates (stops in route order, items in input order), so racks hold whole crates and a split stop fills neighbouring racks. Every rack holding part of a split stop gets a warning. `PlanException` only when the stops exceed the ship (naming the missing SCU and the first stop that doesn't fit) or whole crates don't fit behind the previous stops. Player-facing text numbers racks from 1; `Rack.Index` stays 0-based.
- **Counter-argument:** Items keep their input order; sorting crates large-first would fit some tight routes that now fail with "Crates don't fit". Splitting instead of failing hides an awkward route; the player only sees it in the warnings.
- **Consequence:** "Fewest stops in the fullest rack" isn't additive, so the planner runs its DP once per cap on stops per rack and takes the smallest cap that reaches the fewest splits. That makes the D5 criteria exact; the single pass from T2.1 wasn't guaranteed optimal for ships with many racks. Item reordering can become a task if tight routes fail in practice.

## D7 – Structured planner warnings

- **Context:** The text renderer shows warnings per rack and once in a summary; the overlay will show them on the rack. As plain strings, the rack was only part of the text ("Rack 1: Riker spans racks 1+2").
- **Decision:** `LoadPlan.Warnings` is a list of `PlanWarning(RackId, Message)`. The message reads on its own without the rack; a split stop gets the same message in every rack it spans, so the summary is a `Distinct()` over messages.
- **Counter-argument:** Plain strings were simpler and enough for a log; the renderer could parse the "Rack N" prefix instead of changing the model and the T2.2 tests.
- **Consequence:** No hidden coupling between the planner's wording and the renderer. `Validate` (T2.3) returns `PlanWarning`s too, so an overloaded rack can be highlighted. The player-facing rack number moved to `Rack.Number`, shared by planner and renderer.

## D8 – Hand-written CLI argument parsing

- **Context:** The CLI exists to try the planner on mission files: one command (`plan`), one option (`--ship`).
- **Decision:** Parse `args` with a C# list pattern in `Options.Parse`; anything else prints the usage and exits with 2. No `System.CommandLine`.
- **Counter-argument:** `System.CommandLine` brings `--help`, validation, error messages and tab completion, and scales to more commands without hand-written parsing.
- **Consequence:** No extra package for a debugging tool. If the CLI grows beyond a few commands or options, switching to `System.CommandLine` becomes a task of its own.

## D9 – Rack grid and physical position

- **Context:** Hangar data for the Hull A (Alpha 4.10): four plates on the spindle, 2 sides × 2 levels, each a cell grid of 4 × 2 × 2 (length × width × stack, 1 cell = 1 SCU). The racks don't run front to back, so the old wording was wrong, and the speculative slot model from T1.1 never matched the game.
- **Decision:** A rack has a `Grid` (`Dimensions` in cells) and a `Position` (side, level); the grid volume must equal `capacityScu`. Crate shapes are a fixed table in Core (1 = 1×1×1, 2 = 2×1×1, 4 = 2×2×1, 8 = 2×2×2, 16 = 4×2×2, 24 = 6×2×2, 32 = 4×4×2), never turned. No 3D packer: on a Hull A plate every mix up to 16 SCU fits. An 8 fills two length cells completely; flat 4s have 2 areas × 2 levels = 4 places, each 8 takes 2; 2s and 1s fill any rest; a 16 fills the plate alone. So the SCU sum check from D6 is exact for the Hull A. Shape check (`CanHold`) is per crate, not per mix – the sum argument covers the mix for Hull A; a packer stays out until a ship breaks that argument. The planner rejects a crate that fits no rack before planning.
- **Counter-argument:** Ships with irregular plates may need a real packer, and the sum argument has to be redone for every new grid. `capacityScu` is redundant to the grid. On a ship with racks of different grids, the pre-check only asks "fits any rack"; the planner could still put the crate into a rack that is too small.
- **Consequence:** Rack order stays the planning order, separate from the physical place: "neighbouring racks" in D5/D6 means neighbours in rack order, and on the Hull A Racks 2 and 3 sit on different sides. The overlay has to show rack numbers and draw racks by `Position` (T3.5). A per-rack shape check inside the planner, or a packer, becomes a task once a ship breaks the sum argument.

## D10 – Manual override: hints on move, violations on validate (superseded by D24)

- **Context:** The player can move a placement to another rack (T2.3, drag-and-drop in T3.9). Afterwards the planner's hints can be wrong: a stale "Riker spans racks 1+2" sends the player to a rack without Riker cargo, a missing "Rack 1 shared by …" puts a foreign crate on the lift platform and the hand-over is refused. A move can also overload a rack or put a crate into a rack too small for its shape.
- **Decision:** `MovePlacement(plan, ship, placement, targetRackId)` derives the hints (shared racks, split stops) anew from the placements; `Plan` uses the same derivation. It never refuses a move. `Validate(plan, ship)` returns only violations: more SCU than the rack holds, and crates whose shape the rack can't hold (`Rack.CanHold`, per crate as in D9). Precision in the planning phase, ratified by approval.
- **Counter-argument:** Letting `Validate` return hints and violations would keep the task's `MovePlacement` signature without a ship and keep all messages in one place; the UI would just always call `Validate`.
- **Consequence:** `LoadPlan.Warnings` never goes stale, and "rack in `Validate`" means "can't be loaded" (T3.9 colours it red) without parsing messages. `MovePlacement` needs the ship for rack numbers and to check the target rack. "Copy as text" shows violations only through the rack header (`22/16`). Delivered placements still count towards capacity; the hints leave them out (D16).

## D11 – Click-through as lock mode, default interactive

- **Context:** Games with raw mouse input send clicks to the window under the hidden OS cursor, and in Star Citizen the hidden cursor moves with the view. Reproduced in-game: a crate could not be released because the hidden cursor was over a non-click-through third-party overlay. The overlay must also be clickable while loading (tick off, drag, later the editor).
- **Decision:** Click-through is a mode, `OverlayViewModel.IsLocked`, default `false` (interactive). Locked sets `WS_EX_TRANSPARENT`; unlocked removes only that bit. `WS_EX_LAYERED` stays: WPF sets it itself for `AllowsTransparency` (checked on the running window) and removing it breaks rendering. The style is applied from `SourceInitialized` on, when the HWND exists. Auto-lock (T3.3) locks while `StarCitizen.exe` is in the foreground and `CURSOR_SHOWING` is not set; a manual lock (T3.2, hotkey in T3.7) forces locked as an override: `IsLocked = Manual || Auto`.
- **Counter-argument:** Permanent click-through with a hotkey to unlock would be simpler and never in the game's way; detecting the cursor state polls Win32 and can guess wrong after a game patch.
- **Consequence:** A locked overlay can't be clicked, so unlocking needs a window of its own (T3.2) or a hotkey; until then the `--locked` start switch tests the mode and unlocking means a restart. Clicks on fully transparent pixels pass through WPF windows anyway, so only a click on the dark background proves the mode. Only read-only Win32 queries on other windows, nothing in the game process (EAC).
- **Addendum (T3.2):** The lock window is a second, owned window that never gets `WS_EX_TRANSPARENT`, so it stays clickable while the overlay is locked; a restart is no longer needed. It gets `WS_EX_NOACTIVATE` and an unfocusable button: at the freight elevator terminal the cursor is free, and a click that took the foreground would make Star Citizen lose the mouse. The overlay itself stays as in T3.1 (`DragMove` activates it); changing that is not needed yet (changed by addendum T3.6). The lock sits inside the overlay's top-right corner but stays a window of its own: `WS_EX_TRANSPARENT` covers the whole overlay window and can't spare a button, and `HTTRANSPARENT` only forwards to windows of the same thread. Rejected: a button in the overlay that only locks, with unlocking by hotkey (needs the keyboard, pulls T3.7 forward); polling the cursor over the button (brings back the hidden-cursor problem above).
- **Addendum (T3.3):** Auto-lock reads the cursor state instead of guessing the game's menus: key heuristics (mobiGlas/Esc) can drift out of sync, as seen in-game with a third-party overlay; the cursor is the actual state. `IsLocked = IsManuallyLocked || IsAutoLocked`; the lock window and `--locked` switch only the manual lock. A `DispatcherTimer` polls every 150 ms on the UI thread: `GetForegroundWindow` (process name resolved only on a window change) and `GetCursorInfo`. Rejected: `SetWinEventHook` for foreground changes – Windows has no event for the cursor state, so polling stays anyway. While auto-locked the lock window is click-through as well (amends T3.2's "never"): the hidden cursor could sit over it too, and nobody can aim at it then. `GetCursorInfo` failing throws, except `ERROR_ACCESS_DENIED` on the secure desktop (Win+L, UAC; from experience reports, not documented), which counts as "cursor showing". Spike before the code (Star Citizen hides the cursor with `ShowCursor`; a state with `flags = 1, hCursor = 0` did not occur, so `CURSOR_SHOWING` alone decides). Precision in the planning phase, ratified by approval.

  | Phase | Foreground process | flags | hCursor |
  |---|---|---|---|
  | Main menu | StarCitizen | 1 | game's own |
  | Loading screen | StarCitizen | 0 | 0 |
  | First person / flight | StarCitizen | 0 | 0 |
  | mobiGlas | StarCitizen | 1 | game's own (changes on hover) |
  | Esc menu | StarCitizen | 1 | game's own |
  | Freight elevator terminal | StarCitizen | not logged; overlay unlocks in-game, so `CURSOR_SHOWING` is set | |
  | Typing in Windows Terminal | WindowsTerminal | 0 | 0 |

  The last row is why the foreground process is needed: other programs hide the cursor too. Counter-argument: a game patch can change how the cursor is hidden; the spike table is the reference to check against.
- **Addendum (T3.6):** The overlay gets `WS_EX_NOACTIVATE` too, replacing T3.2's "changing that is not needed yet": ticking a stop off (D16) is the first control meant to be clicked at the freight elevator terminal, the exact case T3.2 named. `WS_EX_NOACTIVATE` also takes a window off the taskbar, so the overlay adds `WS_EX_APPWINDOW` and keeps its taskbar button (the lock window has none). Both windows use `NativeMethods.PreventActivation`. Checked on the running window: ex-style `0x080C0108` (`NOACTIVATE | APPWINDOW | LAYERED`, plus WPF's own bits). Counter-argument: windows that never activate can behave differently while dragged or resized, and keyboard input would need explicit activation – the overlay takes none, the editor (T3.8) is a window of its own. Precision in the planning phase, ratified by approval.

## D12 – App tests run on Windows only

- **Context:** `CargoPlan.App.Tests` targets `net10.0-windows`. The Linux runner compiles it (`EnableWindowsTargeting`) but can't run it: there is no `Microsoft.WindowsDesktop.App` runtime. T0.2 rejected a solution filter as a second command path.
- **Decision:** The test project sets `IsTestProject` to `false` when not building on Windows. `dotnet test` only runs projects with `IsTestProject == 'true'` (VSTest target in the SDK's `Microsoft.TestPlatform.targets`), so one command stays on both runners.
- **Counter-argument:** View models in a separate `net10.0` project would be tested on Linux too, without an MSBuild condition. Linux skips silently: a broken App test only shows in the Windows run.
- **Consequence:** `ci.yml` is unchanged; the Windows run is the only one that runs App tests. Core, Import and Cli tests run on both. If view models grow into logic that needs the Linux check, a separate project becomes a task.

## D13 – Settings in LocalAppData, saved on change

- **Context:** The overlay should stand next to the spindle at the same spot every session. Star Citizen crashes often take the whole PC down (GPU reset, driver), so saving only on a clean exit would lose the position every time. T3.1 planned a timer that re-asserts `Topmost` every 2 s against borderless games.
- **Decision:** `%LocalAppData%\SC-CargoPlan\settings.json` (`SettingsStore.DefaultPath`), not next to the EXE (Program Files needs admin rights) and not roaming `%AppData%` (window bounds belong to this machine's monitors). Model in the app, not in Core: it is UI state. `LocationChanged`/`SizeChanged` restart a 500 ms `DispatcherTimer`, which saves; `Closed` writes only what is still pending. Only in `WindowState.Normal` (minimized reports `-32000`). Listening starts at `ContentRendered`, so startup positioning is no change. Writes go to `settings.json.tmp`, then `File.Move(overwrite: true)`. Restoring clamps the bounds into the virtual desktop (`WindowBoundsRestore.Clamp`, same frame as `LockWindowPlacement`) and enforces the window's `MinWidth`/`MinHeight`. A broken file or unknown `schemaVersion` gives defaults plus a notice line in the overlay and stays untouched until the overlay is moved; a failed write shows a notice, no crash. Strict JSON options like the mission files.
- **Counter-argument:** Saving only on exit is less code and never writes during a session. Clamping to the virtual desktop instead of the nearest monitor can leave part of the window in a gap between monitors of different heights. Strict options make an older app treat a newer file as broken.
- **Consequence:** No settings dialog yet (no setting a user sets by hand); resetting means deleting the file (README). The topmost timer is dropped: in-game the overlay stayed above borderless Star Citizen (T3.1), so there is no proven problem to fix; it returns only with an issue report and a repro (TASKS.md backlog). Precision in the planning phase, ratified by approval.

## D14 – Rack geometry is data; ship view renders boxes from it

- **Context:** The ship view (T3.5b) has to draw racks for every ship that has a JSON file, without a special case per ship. `Rack.Position` (side, level) fits the Hull A's four plates but not a Cutlass bay or the RAFT's three pods. D9 said "draw racks by `Position`"; this entry replaces that sentence.
- **Decision:** Ship file `schemaVersion` 3. Each rack has a required `origin: [x, y, z]`, its minimum corner in whole cells. Coordinates are right-handed: x towards the bow, y towards port, z up; 1 = one cell. Grid axes are fixed to the ship axes (length → x, width → y, stack → z) – a drawing convention, the physical stacking direction is not modelled; no rotation per rack until a ship needs it (`orientation`). The loader (`ShipDto.ToShip`, next to the duplicate-id check) rejects overlapping racks (axis-aligned boxes, touching is allowed) and names both racks by their player numbers. `Position` stays as player wording and is not derived from `origin` or the other way round; a test checks that the Hull A's two agree. `Ship.Bounds` encloses all racks as the frame of the view. The Hull A values are schematic, with one cell of gap for the spindle and between the levels. Rendering: 2.5D isometric boxes first, because the overlay runs next to the game in a software-rendered layered window (D2); `Viewport3D` stays an option on the same data. Crate-exact drawing only if the planner ever assigns cells (its own entry). Precision in the planning phase, ratified by approval.
- **Counter-argument:** `origin` and `position` say similar things twice and can drift apart in a community PR. The overlap check sits in the loader, so a `Ship` built in code may overlap; checking it in `Ship` would force sensible geometry on every test ship. A ship mesh or outline would look like the real ship, but needs an asset pipeline, raises the question whether game data may be redistributed, and costs render time in the layered window.
- **Consequence:** v2 ship files are rejected with "schemaVersion 2 is not supported (expected 3)". Every new ship needs a sketched `origin` per rack (docs/ship-format.md). Planner, text renderer, CLI and import are unchanged. Backlog: rack `orientation`, a `Viewport3D` renderer, a ship mesh outline.
- **Addendum T3.13c:** The fixed mapping "length → x, width → y, stack → z" is replaced by a stack axis per rack, ship schema 4 (D26). `origin` stays the min corner.

## D15 – Ship view: isometric, rack-level, mission colours

- **Context:** The overlay showed the plan as monospace text; at the spindle the player had to turn rack numbers into side and level in their head. T3.5b draws the racks from `Rack.Bounds` (D14) next to the game, in a software-rendered layered window (D2).
- **Decision:** Isometric projection seen from bow, port and above: `u = (y − x)·cos 30°`, `v = (x + y)·sin 30° − z` (screen y down), so the bow points left-down, port right-down towards the viewer, up stays up; the visible faces are top, port and bow. Racks are painted back to front by the depth of their centre (`x + y + z`), ties in rack order (Hull A: 4, 2, 3, 1). Each rack is cut along x into one segment per placement, proportional to SCU, from the bow end in plan order, plus the free rest; an overloaded rack is scaled to its load. The planner assigns racks, not cells, so the view shows shares, not crates. One colour per stop in order of first appearance: Okabe-Ito without its black (invisible on the dark overlay) plus white, 8 colours, repeating from stop 9 with a legend line. Delivered is dark grey, free space only an outline. Rack edges turn red only for violations from `LoadPlanner.Validate` (D10); planner hints colour nothing and stand in the legend word for word (D7). Rack numbers sit on the bow face, painted last with an outline. Placement details (`Rack 1 · port upper · 16 SCU Titanium (4×4)`) show as a tool tip on hover, found by a point-in-polygon test over the projected segments. Wheel zooms around the cursor (0.5×–4× on top of fit-to-view), left drag in the view pans, double-click fits; the view handles its left clicks, so `DragMove` only works on header, legend and border. All logic is pure functions in `CargoPlan.App/ShipView`, the control only transforms and paints. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Centre depth can sort racks of very different sizes wrongly (a long flat rack next to a tall one); a sort by separating axis with a topological order would be exact. A bow pointing left reads against the direction of travel. A tool tip needs hover, so a locked overlay shows no details, and per-segment labels would be readable without the mouse.
- **Consequence:** Exact for the Hull A; a new ship with unequal racks may need the separating-axis painter (backlog). Zoom and pan are not saved (backlog if it bothers). `PlanTextRenderer` stays for the CLI and "Copy as text" (T3.8); the overlay no longer uses it. T3.6 (tick off) and T3.9 (drag and drop) can reuse the hit test.

- **Amended by T3.5c (orbit):** The isometric view is the default camera, not a fixed one. Containers under the hull (spindles all round, pods below the hull) never show from above, so the player turns the camera around z (yaw, wrapped to 0–360°) and tilts it (pitch, positive from above, clamped to ±85° so up stays up). The default is yaw 45°, pitch arctan(1/√2) ≈ 35.26° with the projection stretched by √(3/2): exactly the formula above. Visible faces follow from the view direction (outward normal · direction < 0, edge-on faces left out); bow and aft faces show only the segment at their end, the bottom the same segments as the top. Painter depth is the centre · view direction, rounded to 9 decimals so ties stay ties. The rack number sits on the visible face with the largest projected area (ties: top/bottom, sides, ends), not on the bow face. Mouse: left drag orbits (0.5°/px), right drag pans (on cargo it moves it since T3.9, D20), wheel zooms, double-click resets camera, zoom and pan; locked, all of it does nothing. Fit uses the extent at the current camera. `ShipScene` is camera-independent (built per plan in the view model), `SceneProjector` projects it per camera in the control; the hit test is unchanged on the projected polygons. Precision in the planning phase, ratified by approval.
- **Counter-argument (T3.5c):** Fitting per angle makes the ship breathe slightly while turning; a fit to the bounding sphere would hold still but waste space in the default view. The number jumps faces when two faces are about equal, and the largest face can be covered by a rack in front – the number is still drawn on top. Free orbit can get lost; snapping to fixed angles would be easier to repeat.
- **Consequence (T3.5c):** Backlog: snap to fixed angles, persisting the camera with zoom and pan; the separating-axis painter stays.

## D16 – Delivered per stop; hints exclude delivered, capacity includes it

- **Context:** At the cargo lift the player has to see what is already gone. In the game a mission is unloaded completely at its destination, a split stop (Rack 1+2) included, in one visit; there is no partial unload of a stop. The planner's hints ("Rack 2 shared by Riker, Shubin", "Riker spans racks 1+2") exist to tell crates apart while unloading. D10 says delivered placements still count towards capacity.
- **Decision:** The unit is the stop. `LoadPlanner.SetDelivered(plan, ship, destination, delivered)` sets `Delivered` on every placement of the stop and derives the hints anew without delivered placements (the same derivation `Plan` and `MovePlacement` use); `Validate` keeps counting them towards capacity. The player ticks the stop in the legend – each stop line is a check box – or clicks any of its cargo in the ship view, grey cargo included; both run `OverlayViewModel.ToggleDeliveredCommand`, a misclick is undone by clicking again. In the view a click is a press and release inside the system drag rectangle (`SM_CXDRAG`/`SM_CYDRAG`); the orbit starts only once the drag leaves it, so a click doesn't turn the ship. Double-click resets the view only on free or empty space; on cargo its second click is a click of its own. A delivered stop keeps its place in the legend, struck through and grey, its swatch in the segment grey; "All stops delivered." stands in the header. The ship view must not jump while ticking: its fit depends on its size, and the legend loses hint lines with every delivered stop. So the legend reserves the space of the hints of the same plan with nothing delivered (`ShipScene.ReservedHints`, a hidden list under the visible one) – a function of the plan, not of the click history; active hints are never more or longer than those, a shared rack names a subset of the same stops and a split stop keeps its racks or vanishes. The overlay is clickable only while unlocked, which needs no code: at the terminal the cursor shows, so auto-lock is off (D11). "Copy as text" marks delivered lines with "(delivered)", as the tool tip does. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Hints and capacity now treat delivered cargo differently, which reads like a contradiction to D10. They answer different questions: hints say which crates to pick at the lift, and once Riker is gone, "Rack 2 shared by Riker, Shubin" would make the player look for Riker crates that aren't there; capacity says whether the planned load fits, and a plan stays a plan of what was loaded. Ticking per placement would allow partial unloads the game doesn't have. A click in the view now competes with the orbit drag and with double-click reset: a double-click on the ship to reset ticks twice and resets nothing; a delay for the double-click time would make every tick sluggish. The reserved hint space stays empty after a delivery.
- **Consequence:** `Delivered` lives in the plan and is not persisted yet: it is saved with the plan in T3.8 (a Star Citizen crash between two stops must not lose the ticks). Re-planning after a delivery would need the planner to ignore delivered cargo, not part of this. The stop lines handle their clicks, so dragging the window works on the header, the hint lines and the border. Scene segments carry their destination for the hit test (`SceneHitTest.DestinationAt`; since T3.9 their placement, D20). Backlog if wanted: a hotkey.
- **Addendum (T3.8b):** The stop line is no longer a check box but a plain button without box or frame: the box added nothing the grey and the strikethrough don't show. The whole line stays clickable; a hand cursor says so. Same command, same look of a delivered stop. Precision in the planning phase, ratified by approval.

## D17 – Global hotkeys via RegisterHotKey, no defaults

- **Context:** With the tractor beam, in flight and in a dogfight, Star Citizen hides the cursor; nobody can click the padlock or move the overlay away. T3.7 adds two keyboard actions that work while the game has the focus: switch the manual lock (D11) and hide/show the overlay.
- **Decision:** `RegisterHotKey` on the overlay's HWND, `WM_HOTKEY` through `HwndSource.AddHook` (`HotkeyService`, attached to the overlay's `SourceInitialized`/`Closed` like `OverlayBoundsSaver`). No keyboard hook (`SetWindowsHookEx`): a hook sees every key of every program and is what anti-cheat looks for; `RegisterHotKey` is a plain Windows service. **No default hotkeys:** a registered combination is taken from the focused program, so a default that matches a Star Citizen binding would silently take a game function away; Star Citizen binds many Ctrl, Alt and F-key combinations, so no default is safe. The player sets `"hotkeys": { "toggleLock": "…", "toggleOverlay": "…" }` in settings.json, both optional; an optional field needs no `schemaVersion` bump (D13). `HotkeyParser` accepts Ctrl/Alt/Shift/Win (any case, any order) plus A–Z, 0–9, F1–F24 or a few named keys; Ctrl, Alt or Win is required (Shift+L is a capital L in every chat), F12 is refused (reserved for debuggers by Windows), `MOD_NOREPEAT` is always set so holding the keys toggles once. Our own small table instead of WPF's `KeyGestureConverter`: own error reasons for the notice line. A combination already taken (`ERROR_HOTKEY_ALREADY_REGISTERED`) or an invalid text gives a line in `OverlayViewModel.HotkeyNotice`, the other hotkey still works; a separate property because a successful save clears `Notice`. The hotkeys run the existing `ToggleLockCommand` and the new `ToggleOverlayCommand` (`IsOverlayHidden`). Both windows call `Hide()`/`Show()` themselves: hiding an owner leaves its owned windows visible (only minimizing hides them, Win32 "Owned Windows"), and `Hide()` keeps the HWND, so the hotkeys stay registered. Hiding resets nothing; the auto-lock keeps polling. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Players have to edit a JSON file, and a typo inside `hotkeys` makes the whole file invalid (strict options, D13): defaults plus a notice, and moving the overlay then overwrites the file. `RegisterHotKey` can succeed and still never fire: on the development machine another program swallowed Ctrl+Alt+L before the hotkey check (likely a low-level keyboard hook), undetectable for us. Raw input (`WM_INPUT`) may still show the keys to the game. While hidden, the overlay also leaves the taskbar; only the hotkey brings it back.
- **Consequence:** settings.json is written with the relaxed JSON encoder, so a hand-written "Ctrl+Alt+K" stays readable instead of `Ctrl\u002BAlt\u002BK`. README lists the format and suggests unusual combinations with "check your own Star Citizen bindings". A capture UI (press the keys instead of typing them) is its own task once editing JSON turns out to put players off; the gear icon in the header comes with it.
- **Addendum (T4.4):** The capture UI exists (D35). The notice for a taken combination now points at the settings window instead of settings.json.

## D18 – Plan persisted separately from settings, input and result together

- **Context:** A Star Citizen crash between two stops lost the plan and its ticks (D16): the plan lived in memory, and every start showed the placeholder plan from the test fixture. The player stood at the second cargo lift without knowing which rack held what. Settings already survive crashes (D13), but they are preferences, the plan is work in progress.
- **Decision:** `%LocalAppData%\SC-CargoPlan\plan.json` (`PlanStore.DefaultPath`), a file of its own next to settings.json: deleting the settings to reset the window (README) must not throw away the plan, and the other way round. The file holds the input and the result (`docs/plan-format.md`): the missions as a complete mission file, the placements with rack and `delivered`, and the planner's hints; `shipId`, `schemaVersion` 1. The plan can't be planned again from the missions once it has a move (D10) or a tick. Hints are stored, not derived again on loading: the derivation is private to the planner, which stays unchanged. Reading and writing live in Core (`PlanFile`, `SavedPlan`), next to the mission and ship formats, so the CLI can use them without the overlay; `SavedPlan` checks in its constructor that the placements cover the missions exactly (SCU per destination, commodity, crate size), and `PlanFile.Read` checks the ship and its racks. Overloaded racks and crates that don't fit are allowed (D10). `PlanSaver` listens to `OverlayViewModel.Plan` itself, not to single commands, so every way of changing the plan saves it (tick now, editor and drag and drop later). Saving is debounced by 500 ms like the window bounds, written atomically (`AtomicFile`, shared with settings.json), and `Closed` writes what is still pending. A missing file starts with the empty ship and "No plan. Open the editor to enter missions."; a broken file, another ship or a plan that doesn't match its missions starts empty with a notice, and the file stays until the player makes a new plan. `--plan <file>` loads a plan file instead (development aid, replaces the embedded placeholder) and becomes plan.json on the next save. Notices become a list with a source (`NoticeSource`: settings, hotkeys, plan); each source sets and clears only its own line. This replaces `Notice` and `HotkeyNotice` from D17. `plan.EnsureBelongsTo(ship)` is the one ship check for planner, text renderer, ship view and plan file. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Ticks are single clicks, not a stream of events like dragging the window; saving at once would need no timer and would also keep a tick made less than 500 ms before a crash. Stored hints keep an older wording until the next tick or move derives them anew. The missions carry a second `schemaVersion` inside the file. Every start with a plan writes plan.json once, unchanged, because the saver is attached before the start plan is shown.
- **Consequence:** A crash or a kill keeps the plan and every tick older than half a second. A plan file for another ship shows a notice; with a ship selection (T7.1) the reader will have to look up the ship from `shipId` first. The editor that writes new plans, with import and export, came with T3.8b (D19); discarding a plan without a new one is backlog.

## D19 – Mission editor: row per cargo item, inline validation, draft until Plan

- **Context:** Until T3.8b a plan only came from a file (`--plan`). At the mission board the player accepts three to five contracts and walks to the cargo lift; entering them must take less than two minutes, or nobody does it. TASKS.md asked for a `DataGrid` with Destination / Commodity / SCU / Crate size, `PlanException` as a MessageBox, import and export of mission files, and "Copy as text".
- **Decision:** `MissionEditorWindow`, opened by a pencil in the overlay header (left of the padlock, hidden while locked) and by an "Open editor" button in the empty state; one editor at a time. A normal window: it takes the focus on purpose, no `WS_EX_NOACTIVATE`, no click-through. Owned by the overlay, so it is topmost too (owned windows of a topmost window are topmost, `SetWindowPos`), closes with it and hides with the overlay hotkey. It also hides while auto-locked: left open in flight it would catch the tractor-beam click (D11); `ShowActivated=False` applies to every `Show()`, so it comes back without taking the focus, and opening calls `Activate()`. **One row = one cargo item**; stops follow the first appearance of their destination (case-insensitive, trimmed, first spelling wins), a read-only column shows the stop number. New rows come from the data grid's new-item row (Tab from the last cell) or the Add button and take the crate size of the row above (first row 1, valid for any SCU); ↑/↓ move rows, "Clear rows" empties the draft for the next route. Blank rows are skipped. **Validation inline:** red row with the reason as tool tip, the first problem in a status line, "Plan" disabled while a row is invalid; rules: destination and commodity not empty, SCU a whole number above 0 and a multiple of the crate size, crate size from the list. **`PlanException` goes into the status line, not a MessageBox** (precision against the TASKS text): a modal box covers the grid and needs a click before the player can fix the SCU number. **Rows are a draft until "Plan":** `LoadPlanner.Plan` → `SavedPlan` → `OverlayViewModel.ShowPlan`, saved by the existing `PlanSaver`; closing without "Plan" keeps the overlay's plan, the title says "unplanned changes". **Planning again starts a new plan:** ticks and moves are gone; with ticked stops the status line says "Planning again clears delivered marks." beforehand, no confirmation box. Import (`MissionFileReader`) replaces the rows, export (`MissionFileWriter`, new in Core, written through `AtomicFile`) writes the current rows, planned or not; "Copy as text" copies `PlanTextRenderer.Render` of the overlay's plan. Problems with files and the clipboard go into the status line. **A successful "Plan" closes the editor:** the plan is in the overlay and the next step is loading in the game; a `PlanException` keeps it open for the fix. Conversion and checks are a pure function (`MissionRows.ToStops`/`FromStops`), the editor state is `MissionEditorViewModel`; dialogs and clipboard stay in the window's code-behind. No ship selection, no saved editor position, no draft autosave, no undo. Precision in the planning phase, ratified by approval.
- **Counter-argument:** The SCU rule now lives twice, in `CargoItem` and in `MissionRows`, because `ArgumentException` appends "(Parameter 'Scu')" to its message; a test checks every crate size against SCU 1–64 so they can't drift apart. A row turns red as soon as it has content, while it is still being typed. The status line shows only the first problem. Re-planning throws away manual moves too, once drag and drop exists (T3.9). "Clear rows" has no undo; closing without "Plan" brings the old rows back on the next opening. An editor left open reappears whenever the cursor shows, mobiGlas included. Closing on "Plan" leaves nothing to check in the editor, and "Copy as text" right after planning needs it opened again (prefilled, one click).
- **Consequence:** The MVP loop runs without a terminal: enter, plan, overlay, tick, restart. Discarding a plan without a new one is not possible (backlog). Planner hints show in the overlay legend, not in the editor. `--plan` stays as a development aid.
- **Addendum (T4.2a):** The gear of the settings window now sits between the pencil and the padlock (D34); the pencil moved one button to the left. The hide rule is `OverlayViewModel.AreToolWindowsHidden`, shared with the settings window. Precision in the planning phase, ratified by approval.

## D20 – Override by right drag; placement level; overload allowed (overload superseded by D24, gestures by D25)

- **Context:** T2.3 gave the planner `MovePlacement` (D10), the overlay had no way to use it. Two cases from the game, both with a free cursor at the cargo lift: before loading the planner's racks don't suit the situation (the platform sits on the other side, heavy cargo should go to one side), or while loading a crate lands in the wrong rack and the plan should follow what is on the plate, not the other way round.
- **Decision:** **Right drag on cargo moves its placement** to the rack under the cursor on release; right drag anywhere else pans as before (D15), left stays orbit and click everywhere. Left drag on cargo is orbit today, and zoomed in nearly everything is cargo: orbit must not depend on where the drag starts. Keyboard modifiers were checked (A3) and are possible, not impossible: WPF's `Keyboard.Modifiers` reads `GetKeyState`, the key state of the thread's own message queue, which a `NOACTIVATE` overlay never gets keyboard messages for; but `WM_LBUTTONDOWN`/`WM_RBUTTONDOWN` carry `MK_SHIFT`/`MK_CONTROL` in wParam without focus (learn.microsoft.com, WM_RBUTTONDOWN). Rejected anyway: Shift+left needs a `HwndSource` hook to read wParam, and the key goes to Star Citizen in the foreground; right drag needs the mouse only. **The unit is the placement, not the stop:** a split stop can be moved in parts, so Riker 16 + 4 can be joined into one rack and the split hint goes. Delivered placements can't be picked up, the crates are gone (D16); a right drag from them pans. The target is any face of the rack, free space and frame included; the same rack or no rack is no move. While dragging, the placement is drawn faded in place and the target rack gets a cyan edge (`MissionPalette.DragTarget`); no ghost following the mouse. **Overload is allowed:** after the drop `Validate` turns the rack red with its line in the legend, as since T3.5b; no dialog, no snapping back. The player knows what is physically on the plate; the tool reports, it doesn't intervene. Undo = drag back. The rules are one pure table, `DragGesture.Resolve(button, hit at press, moved, hit now)`, asked on every move and on release; `OverlayViewModel.MovePlacementCommand` takes its `Gesture.Move` record. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Right drag is harder to discover than left (the README says it), and on cargo it no longer pans: zoomed in, panning needs free space or the area next to the ship. The legend can jump on a move, because the reserved hint space is computed from the new plan (D16); moving is editing, not ticking, so that is accepted. A modifier gesture would have kept right drag as pan everywhere.
- **Consequence:** Scene segments and strips carry their `Placement` instead of the destination, racks their `RackId` (`SceneHitTest.HitAt`). Two equal placements in one rack (after moving back and forth) fade together; `MovePlacement` moves the first, they are interchangeable. A scene change during a drag cancels it, so no placement of an old plan reaches `MovePlacement`. Moves are saved through `PlanSaver` like ticks; **Plan** in the editor makes a new plan and drops them (D19). Core is unchanged. Not in T3.9: undo, a ghost image, dragging in the legend, moving whole stops, animation.

## D21 – Cells, not segments; fill order is schematic and parameterised

- **Context:** Since T3.5b each rack was cut along x into one segment per placement, proportional to SCU (D15). In the game crates go onto the plate in layers; "12 SCU Riker" as one full layer plus a row is easier to grasp at the spindle than a 75 % bar. Later a coordinator of a large ship should show every hauler the same picture, fill direction included. This entry replaces D15's sentence about segments.
- **Decision:** Each rack is drawn as its grid of 1-SCU cells (`Rack.Grid`, D14: the grid is ship data); placements in plan order take one cell per SCU (`RackCells.Build(rack, placements, FillOrder)`), the rest is free. **Fill order:** layer by layer from the bottom (z, the drawing axis of stack, D14); in a layer row by row from the centreline outwards (smaller |y| first, so port and starboard racks fill as mirror images); in a row along the length from the bow (`FillOrder.BowFirst`) or the stern (`SternFirst`). The order is a drawing, not where a crate goes: the planner assigns racks, not cells. BowFirst is the default, set in one place (`OverlayViewModel.FillOrder`, a constant); `ShipViewBuilder.Build` takes it without a default. **Overload** (after a manual move, D10): the cells are shared by SCU (largest remainder) and every placement keeps at least one cell, so it can still be dragged out (D20); the rack is red as before. **Drawing:** each cell is a box of 0.9 cells with its visible faces; one painter over all cells of all racks by the depth of the cell centre, ties by rack number, then fill order – exact, all cells are equal boxes on one grid. Cargo cells are filled with a thin edge, free cells are a faint outline only, delivered grey, dragged cells faded. Plain rack edges go before the cells, so cargo in front covers them; red (violation) and cyan (drop target) edges and the numbers go after them. **Hit test:** the rack still comes from its faces (free cells and gaps are drop targets, D20); the placement is the rack's frontmost cargo cell at the point, so cargo seen through a free outline answers. Core is unchanged. Precision in the planning phase, ratified by approval.
- **Counter-argument:** A drawn order can be read as a loading instruction although it isn't one; the README says so. An overloaded rack breaks "one cell = one SCU". Rows from the centreline assume y = 0 is the centreline, true for ship files (port = positive y) but not checked. Segments cost 3 polygons per placement, cells 3 per SCU: the Hull A has 64 cells (192 polygons), a Hull C would have about 4,600 (≈ 14,000 polygons per redraw), fine on demand, borderline while orbiting; a synthetic 1,000-cell rack projects in a few milliseconds (test limit 50 ms). Free outlines show the cells behind them, which looks busier than the old faint fill.
- **Consequence:** Where the fill order lives once it is configurable stays open on purpose: shared between a coordinator and the haulers it belongs to the plan (`plan.json`), as a personal preference to `settings.json`; decided when the coordinator scenario is built. (Decided in D24: the plan.) Backlog: a fall-back to segments above some cell count once a large ship exists, crate sizes as blocks, cell labels, numbers and lines of constant size while zooming. Not in T3.10: the fill order in the UI or in any file.
- **Addendum T3.11b – crates as boxes:** To move crates (T3.11c) the player has to see them. `RackCells.Build(rack, placements, order, isViolated)` lays each crate as a block of its shape (`CrateSize.Dimensions`, D9, never turned) at the first free place in the fill order above: of all places it fits, the one whose first cell comes first, on a tie whose last cell does. **The largest crate goes first** (ties in plan order): in plan order Riker's two 4 SCU crates would take the whole bottom layer and Shubin's 8 SCU crate (2 cells high) would fit nowhere, although every mix up to 16 SCU fits a Hull A rack (D9). A placement with a crate that fits nowhere goes cell by cell as a whole, crate after crate into the free cells in fill order; a red rack has no blocks; an overloaded one keeps its shares by SCU (above) and has no crates, the tool tip names the placement as before. Every crate carries a `CrateId(Placement, Number)`, a value that stays the same over rebuilds; equal placements in one rack count on (D22), so ids never collide. Tool tip per crate: `Shubin · Rack 2 · port lower · 8 SCU Agricium crate (1 of 1)`; `SceneHit` carries the crate. The block code knows only grid positions and their rank in the fill order: a different stacking axis (backlog `orientation`) changes `Positions` and the grid-to-ship mapping, not the blocks. **Drawing:** a crate is one box (`SceneBox`), 0.05 cell smaller on every side like a cell, so the gap is the same everywhere; three visible faces, no inner edges. Free cells and cells drawn on their own stay single boxes. This replaces the centre-depth painter (D15, D21 above): boxes of unequal size need **the separating-axis painter** from D15's backlog. Two disjoint axis-aligned boxes always have an axis that separates them; the one beyond it, seen from the camera, is drawn first (`DrawOrder.Compare`). For every pair whose screen outlines overlap (a sweep along screen x, not every pair) that gives an edge; a topological sort (Kahn) starts from the centre-depth order and always takes its earliest free box, so equal cells keep their old order. A cycle (possible for three boxes like a pinwheel, rare on a grid) keeps the centre-depth order and writes a line to the debug log. The same painter sorts the racks; the boxes are drawn rack by rack. A first try drew crates as cells with the inner faces left out and alternating shades; antialiasing left hairlines inside a crate, so it was dropped. Core is unchanged. Precision in the planning phase, ratified by approval.
- **Counter-argument (addendum):** The colours in a rack no longer follow the route: Shubin's 8 SCU crate sits before Riker's 2 SCU crates. The painter is a graph and a sort instead of one line, with a fall-back that only shows in the debug log, which a release build doesn't write: a cycle in the field is drawn by centre depth without notice. Drawing rack by rack is only right while racks stay apart as on the Hull A; racks that interlock would need their boxes sorted together. Translucent fills show the edges of crates behind, which can look like lines inside a crate. The picture is still schematic: the game decides where a crate lands.
- **Addendum T3.13c:** Rows no longer fill from the centreline outwards: `CrateLayout` fills width rows in grid order and the port/starboard mirror comes from the rack's stack axis (D26).
- **Addendum T3.13b:** `RackCells` is gone; its layout rule lives on as `CrateLayout` in Core (D24), and the view draws the stored positions. `CrateId` is the `Crate` itself; shares of an overloaded rack and cell-by-cell fallbacks no longer exist.
- **Addendum T4.6:** The backlog item "numbers and lines of constant size while zooming" is done (D32). The lines were constant already: zoom scales the points, not the drawing, so every pen is in screen pixels.

## D22 – Crate-granular moves with split and merge (superseded by D24)

- **Context:** At the cargo lift the player decides crate by crate ("two more Shubin crates onto the other plate, then it fits") or stop by stop (a whole destination changes sides). Since T3.9 the unit of a move was the placement (D20), so a stop could only change racks in the parts the planner made. Crate sizes are what you enter; the game only shows totals. Enter one row per crate size as you see the crates at the elevator. The contract names only the total SCU and an upper crate size, the kiosk only amounts, so the tool knows the crates only from the player's rows; the editor default for a new row stays "crate size of the row above, first row 1".
- **Decision:** `LoadPlanner.MoveCrates(plan, ship, moves, targetRackId)` with `moves` as `(Placement Source, int Scu)`: each move takes whole crates of its source (SCU above 0, a multiple of the crate size, at most what the source holds, otherwise `ArgumentException` with the numbers); the rest stays, a source without rest disappears. In the target rack the crates **join** a placement of the same destination, commodity and crate size that isn't delivered, at that placement's place in the plan; without one, all crates of a source keep the source's place (the old `MovePlacement` behaviour) and a part goes to the end of the plan, i.e. behind the target rack's cargo. Delivered placements are no source (D16, D20: the crates are off the ship). Sources are matched by value against the original plan; equal placements (twins) are interchangeable, each move takes the first one not yet taken, so naming one placement twice is an error. A source already in the target rack is no move. Afterwards every rack holds at most one placement per destination, commodity, crate size and delivered state – the whole plan is joined, not only the target rack, so twins the planner makes from two equal mission rows go with the first move. Hints are derived anew, overload is allowed (D10). `MovePlacement` is `MoveCrates` with all crates of one placement; `MoveStop(plan, ship, destination, targetRackId)` is `MoveCrates` with all crates of the stop still on board, so Riker 16 + 4 in Rack 1+2 becomes one placement of 20 in the target rack; a delivered stop moves nothing, an unknown destination is an error. The planner itself is unchanged. This replaces D20's sentence about two equal placements in one rack. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Joining forgets which part the planner put where; the only undo is dragging back, and that gives the joined amount, not the old parts. Joining the whole plan changes placements the player didn't touch (planner twins), visible only as one text line instead of two. Moves apply one after the other, so with several sources the order of the list decides which one keeps its place in the plan. Crate sizes typed wrong at the board are moved wrong as well; the tool can't check them against the game.
- **Consequence:** Placements become a set per rack and cargo kind, which the ship view can draw as crates (T3.11b) and the selection can move crate by crate (T3.11c). `SavedPlan` still holds: split and join keep the SCU per destination, commodity and crate size. Whether `MovePlacement` stays once the overlay moves crates is decided in T3.11c (renumbered T3.14 by T3.12).

## D23 – Crate mix derived from SCU and max crate size

- **Context:** A hauling contract names two numbers per destination and commodity: the SCU and the largest crate size it allows ("4 SCU or smaller"); ContractTracker stores the same two. Since T3.8b the player entered one row per crate size, guessed or looked up at the elevator (D22: "Crate sizes are what you enter"). Observed by Martin and checked by three other players in Alpha 4.10: the freight elevator delivers greedily, the largest allowed crate as often as it fits, the rest in smaller ones (6 SCU at max 4 → 4 + 2; 15 at max 4 → 4 + 4 + 4 + 2 + 1). Evidence: our own kiosk screenshot, to follow in `docs/images/` (TASKS.md, T3.12).
- **Decision:** `CrateMix.Decompose(scu, max)` in Core derives the crates from one list, `CrateMix.Sizes` (32, 24, 16, 8, 4, 2, 1), every size up to the max, largest first. **If the game changes, `CrateMix.Sizes` or `Decompose` is the only place to touch; users can override per item in the meantime.** The override is a list of crates per item; `CrateMix.Problem` is its one rule (sizes known, none above the max, sum = SCU) for the file, the input type and the editor. **Expansion, not a model change:** `CargoItem` stays one commodity in one crate size; the input is `MissionItem` (commodity, SCU, max, optional crates) in `MissionStop`, and `MissionItem.ToCargoItems()` is the one place that turns it into one `CargoItem` per crate size, largest first (15 / 4 → 12, 2, 1). Planner, hints, renderer and ship view are unchanged. `MissionFileReader` returns the input, so the editor shows a row as typed; `SavedPlan` keeps it and checks its placements against the expanded items. Mission files go to **schema 2** (`maxCrateSize`, optional `crates`); schema 1 stays readable, an item becoming its explicit crates (max = crate size), so an old file plans exactly as before; the writer always writes 2, `crates` only for an override. plan.json keeps `schemaVersion` 1 and reads both mission versions inside. Editor: Max crate (default the row above, first row 4, the most common entry-level contract) and Crates (the derived mix as text; editing starts empty and takes "2+2+2", empty = derived again; typed crates in italics, kept as typed even if equal to the derivation). This replaces D22's sentence about entering crate sizes. Precision in the planning phase, ratified by approval.
- **Counter-argument:** One contract item now has two shapes, a `MissionStop` in the editor and the files and `Stop`s with cargo items in the plan, and every caller before the planner needs `.ToStops()`; an optional field on `Stop` would have avoided the second type but put an input detail in front of the planner. The rule is an observation, not game data: one patch can break it unnoticed, and 24 SCU at max 32 → one 24 is the case most likely to be wrong. Schema 1 items show as overrides although nobody typed them. Editing the crates starts empty, so changing one crate means typing the whole list.
- **Consequence:** Entering a contract is two numbers again, as T5 (ContractTracker) delivers them. Crates as the primary unit, crate positions (T3.13, D24) and checking the max against the contract text are not part of this.
- **Addendum T3.15:** Split and merge in the overlay (D27) set an item's override too, sorted largest first, and drop it once the crates are the derived mix again: nobody typed it, so "kept as typed" doesn't apply. An override typed in the editor stays as typed until a split or merge touches its item.

## D24 – Crates carry positions; layout in Core; no overload

- **Context:** Until T3.13 the plan knew racks, not cells (`Placement`); the ship view made up where a crate lies (`RackCells`, D21 "schematic"), and D14 kept crate-exact drawing for the day the planner assigns cells. At the cargo lift, and later for a coordinator of a large ship, it matters *where* a crate lies, and when the plate drifts from the plan (a crate landed elsewhere) only stored positions can be corrected.
- **Decision:** The **crate is the unit of the plan**: `Crate(Destination, Commodity, CrateSize, RackId, Position, Delivered)`, `GridPosition(Length, Width, Stack)` from the rack's min corner, stack away from the plate. `LoadPlan.Crates` is the truth; `Placements` is **derived** on every read (grouped by rack, destination, commodity, crate size, delivered; order of first appearance), so hints, legend, text renderer and `SetDelivered` work as before; equal mission rows now give one placement, not twins. **Layout in Core:** `CrateLayout.Place` is the old drawing rule (largest first, fill order, first fit by rank) plus the **support rule**: every cell of a crate's bottom above the plate needs a cell of another crate right below (cargo grid in the game, confirmed by Martin); delivered crates keep their cells and carry. `LoadPlanner.Plan` lays out each rack after assigning racks; for the Hull A every mix up to 16 SCU of 1/2/4/8/16 fits with the support rule (exhaustive test, D9 still exact). The fill order moves to Core and is **stored in the plan** (default bow first), so everyone loading it sees the same layout; this answers D21's open question. **No overload:** `MoveCrate(plan, ship, crate, rack, position)` and the re-layout moves `MoveStop`/`MovePlacement` refuse what doesn't fit (taken, outside, no support, a crate losing its support; nothing slides down) with a `PlanException` and the reason; caller errors (unknown crate, rack or stop, delivered cargo) stay `ArgumentException`, so the overlay catches only refusals and shows them in a notice line. `Validate` reports overlap, crates outside or too large, and crates without support. `plan.json` **schema 2**: `fillOrder` and `crates` with `position: [l, w, s]`; a crate outside its rack, an unknown rack or a crate count that doesn't match the missions is a broken file, overlap and missing support load and show red. Schema 1 is **migrated on reading**: its placements are laid out exactly as the planner lays out a fresh plan, ticks kept, and the overlay writes schema 2 on start (D18); an upgrade must not throw away the plan of a running route (D13's "broken = defaults" is for garbage, not for a known older schema). A schema 1 rack overloaded under D10 has no layout and is refused like a broken file. Replaces D10 (overload allowed), D20's "Overload is allowed" and D22 (split and merge). Precision in the planning phase, ratified by approval.
- **Counter-argument:** Positions are claims about the game: the plan says where a crate lies, the elevator decides, and a coordinator's picture can be wrong in more detail than before. The plan format grows by a field per crate, and every new ship needs the support argument redone. Refusing instead of red can annoy at the lift when the player knows better (one cell off is already a refusal); `PlanException` now also means "move refused", not only "planning failed". Delivered crates blocking their cells is right for ticking back, wrong for using space freed at a stop.
- **Consequence:** The view renders stored positions; the only layout is `CrateLayout` (T3.13b: `ShipViewBuilder` draws `plan.Crates` at `Rack.Origin + Position`, free cells are the cells no crate takes, `RackCells` is gone and with it the view's fill order parameter). A crate a problem names (`CrateLayout.Faulty`, read from the same findings as `Problems`) gets a red outline on top, so in a hand-edited file the player sees which crate overlaps or floats, not only which rack; overlapping crates are both drawn. The tool tip counts a crate within its derived placement in plan order. Right drag moves a placement as a whole by re-layout; dragging single crates to a cell came with D25. Not part of this: sliding crates down, undo, gravity, turning crates.

- **Addendum (T4.5):** The fill order is chosen in the mission editor (**Fill order**: Bow first / Stern first, the word of the `fillOrder` key) and passed to `LoadPlanner.Plan`; it takes effect with the next Plan, like the rows a draft until then, and marks unplanned changes. The editor starts with the current plan's order (bow first without a plan); Clear rows and Import keep it, because it belongs to the player's way of loading, not to the missions. Mission files don't carry it: exporting a route shares the missions, not the order (backlog, a mission file format change in Core). Precision in the planning phase, ratified by approval.

- **Addendum (spike T5.4): delivered cargo frees its cells; stacking follows the route.** Ratified by approval.
  - **Context:** From the game (Martin): delivered cargo is off the ship, and loading new crates where it lay is the player's active decision; a crate with another on top along the stack axis can't be taken away. Spike T5.4: `CrateLayout.Place` lays out by size, not by route, so in a full Hull A (A 20, B 12, C 16, D 16 SCU in 4 SCU crates) B lies on A in rack 2, although A is unloaded first.
  - **Decision:** "Delivered crates keep their cells and carry" is replaced: delivered crates neither take cells nor carry in placement and plan checks; moves use the same checks, so D25's "carry and are drop targets" follows. **Stacking rule:** a crate may only rest on crates that are unloaded no earlier than it is, its own stop or a later one; never a later stop on an earlier one. An earlier stop on a later one is right: the upper crate goes first. The order is the plan's stop order (legend, route). One rule in `CrateLayout`, used by the layout (`Place`) and by the checks (`Problems`, `NewProblem`). A delivered stop whose cells are taken again can't be ticked back, and a drag that breaks a rule is refused, both with the reason (D41).
  - **Counter-argument:** The layout is coupled to the route: whoever flies another order on a whim meets a layout at the elevator that doesn't fit there – like the legend order today, but with consequences for stacking. Ticking back stops being an undo once the cells are reused.
  - **Consequence:** Built in T5.4a, before T5.4; `PlaceInto` (D41) inherits both rules. Plans that today fit only by stacking a later stop on an earlier one have to lay out differently.

## D25 – Drag to cell; selection by right-click; stop moves from the legend

- **Context:** Since D24 crates carry positions, but the overlay's right drag still moved a whole placement by re-layout (D20). At the cargo lift the plate drifts from the plan by single crates: one landed a cell further, one sits on another stop's crate. The plan has to follow that crate to that cell, and sometimes a whole stop has to change racks. Mouse only: the overlay never takes the focus, and every key goes to Star Citizen (D20).
- **Decision:** **Right drag on a crate still on board puts it on the cell under the cursor**, in the same or another rack; right drag elsewhere pans, left stays orbit and click (D20). **The cell is what the cursor shows**, seen like the hit test (D21: free cells are outlines, cargo behind them answers): a crate on the line of sight takes the drop on top of it, over the cell the line meets ("put it on a crate"); without one, the frontmost free cell's column takes it, falling onto the next crate or the plate ("put it into a gap"). The min corner of the crate goes there; a crate as high as the grid, the frame or empty space is no target. The dragged crates are air for that line, so a crate can move one cell over. A first rule, the last free cell along the line of sight, was dropped in the implementation: in the default view it leaves an empty Hull A rack sideways, the outer row on the plate couldn't be reached and the ghost appeared cells away from the cursor. **Validity is Core's:** `LoadPlanner.MoveCrates(plan, ship, moves)` with `CrateMove(Crate, RackId, Position)` is **atomic** – every crate leaves its cells, then all take the new ones, then the rules of `CrateLayout.Problems` run over the result (so crates of one move may carry each other); `CrateLayout.NewProblem` reports only what the move breaks (a problem of a file edited by hand stays out), and `LoadPlanner.MoveProblem` returns that text for the racks touched. The preview asks the same function the drop does (`CrateDrop` in the view): a **ghost** at the target, cyan where it fits, red where it doesn't with the reason as tool tip; releasing on red moves nothing and the notice line says why (D24). Nothing slides down. `MoveCrate` is `MoveCrates` with one move; `MovePlacement` and the overlay's placement drag are gone (this answers D22's open question). **Legend:** right drag of a stop line into the view runs `MoveStop` on the rack under the cursor (re-layout in the plan's fill order); the stop's crates fade, the target rack gets a cyan edge, refusal goes to the notice line; a stop already wholly in that rack stays as it is. Left on the line stays the tick (D16); delivered crates can't be dragged but carry and are drop targets (D24). **Selection** (T3.14b): right click on a crate toggles it, on free or empty space clears; a drag from a selected crate moves the whole selection with every crate keeping its offset in ship coordinates (origin + position, D14) to the anchor; a crate landing in no rack makes the whole move invalid. The selection is view state, not saved, and goes with every plan change and with the lock: `CrateSelection` is bound to the scene it was made in, and every plan change builds a new scene, so no crate of an old plan reaches Core. A right click on a delivered crate keeps the selection. Selected crates get a magenta edge (`MissionPalette.Selection`), the fill stays the stop colour; while dragging, every crate of the selection shows its ghost, and a selection reaching past every rack shows the grabbed crate's ghost red with "A selected crate would land outside the racks." (`CrateMove.Shift` returns null, `CrateDrop.OutsideRacks`). Precision in the planning phase, ratified by approval.
- **Counter-argument:** The column rule is gravity at aiming time, which is what "nothing slides down" was meant to rule out for moves; a floating target can no longer be picked on purpose for a 1 SCU crate, only a larger crate can still hang over an edge. Refusal texts are now the findings' wording ("Crates of Orison and Riker overlap in rack 2"), less specific about which crate moved than the old `MoveCrate` sentences. The ship scene now carries the plan and the ship so the view can ask Core while dragging; a delegate bound from the view model would have kept the scene a pure drawing. The min corner, not the grabbed cell, goes to the target: grabbing the far end of a 4 SCU crate and dropping it puts its near end there.
- **Consequence:** At the lift the overlay follows the plate crate by crate; a whole stop changes racks from the legend. Undo is dragging back. Not part of this: a selection rectangle, keyboard modifiers, undo, turning crates, sliding crates down, middle drag, dragging between overlays.
- **Addendum T3.13c:** `CrateMove.Shift` keeps the ship offset only for a selection over several racks. A selection from one rack keeps its grid offsets to the anchor, so a stack stays a stack between racks stacking in opposite directions (port +y, starboard −y, D26). Over several racks each crate's box moves by the anchor's box offset and lands in the first rack, in rack order, whose grid holds its min corner (`Rack.ToGrid`), otherwise the move is invalid as before. Precision in the planning phase, ratified by approval.
- **Addendum T3.15:** The selection is no longer the view's alone: `ShipViewControl.Selection` is a two-way dependency property bound to `OverlayViewModel.Selection`, so the header's split and merge buttons (D27) can read it and select the crates they made. It is still not saved and still bound to its scene. Precision in the planning phase, ratified by approval.

## D26 – Stack axis is rack data

- **Context:** D14 fixed the grid to the ship axes (length → x, width → y, stack → z) as a drawing convention and left the physical stacking direction to the backlog (`orientation`). In the game it differs per rack (Martin): the Hull A's spindle plates stack from the spindle outwards, interior floors stack up, hull undersides stack down; crates always lie flat against their plate (D9). The overlay drew the Hull A's crates on top of each other where the game puts them side by side, so the in-game check open since T3.10 (2 × 8 SCU in Rack 1) could not pass.
- **Decision:** Ship file `schemaVersion` 4. Each rack has a required `stackAxis`: `"+x"`, `"-x"`, `"+y"`, `"-y"`, `"+z"` or `"-z"`, the ship direction away from the plate. One axis, no orientation triple: length lies along x (on z when the stack is ±x), width takes the remaining axis; a negative axis counts from the rack's max side, so `origin` stays the min corner. Hull A: Rack 1/2 `+y`, Rack 3/4 `-y`, same bounds as before. The grid stays abstract: `CrateLayout`, the support rule (D24, along stack), `Problems` and moves work in grid coordinates; the **only** grid-to-ship mapping is `Rack` in Core (`Bounds`, `CellBox(position, size)`, its inverse `ToGrid(box)`), used by the view, the ghost, the drop target and `CrateMove.Shift`. Width rows fill in grid order: the old "centreline first" rule read `Origin.Y`, which with width on z measures nothing; the port/starboard mirror now comes from the stack axis. `Shift` keeps grid offsets within one rack (D25 addendum). Racks built in code default to `+z`, the old convention. Precision in the planning phase, ratified by approval.
- **Counter-argument:** One axis can't describe a rack turned in its plane or tilted; an orientation triple could, at the price of a format nobody fills in correctly by eye. Grid order instead of "centreline first" is a new drawing rule, and starboard layouts of new plans differ from older ones. `Shift` now has two semantics, chosen by whether the selection spans racks. A rack built in code without an axis silently stacks up.
- **Consequence:** v3 ship files are rejected with "schemaVersion 3 is not supported (expected 4)"; every new ship names its axis per rack (docs/ship-format.md, read it from Erec's guide or in the hangar). Saved plans need no change: positions are grid positions. On a rack stacking along ±x, length runs along z and "bow first" fills from the top. Replaces D14's sentence "Grid axes are fixed to the ship axes" and D21's centreline rule; free rotation per rack stays backlog until a ship needs it.

## D27 – Split and merge within the footprint

- **Context:** The kiosk sometimes delivers other crates than the derived mix (D23): two 2 SCU crates instead of one 4. The plan then shows crates the plate doesn't have, and the player can't follow it. D24 removed D22's split and merge of placements; with crates as the unit they come back as operations on single crates, under the game's rules: fixed sizes only (1/2/4/8/16/24/32), one commodity and one destination, a merge only when the sum is a crate size again.
- **Decision:** `LoadPlanner.SplitCrate(saved, ship, crate[, parts])` and `MergeCrates(saved, ship, crates)` work on the `SavedPlan`, so plan and missions change together. **Footprint rule:** a split lays its parts with `CrateLayout.PlaceWithin`, the layout rule restricted to the old crate's cells, largest first; a merge needs the crates' cells to be exactly the box of the new size in its only orientation (`CrateLayout.BlockProblem`: overlap, "not adjacent", "don't form a block", "would be a 4×1×1 crate, 4 SCU crates are 2×2×1") and puts the crate at their min corner. Either way no cell changes owner, so nothing above or beside loses support and no new finding is possible; the hints are derived anew and stay. **Default split without a dialog:** the two largest parts that add up and fit (`CrateMix.DefaultSplit`: 2 → 1+1, 4 → 2+2, 8 → 4+4, 16 → 8+8, 24 → 16+8, 32 → 16+16); finer is splitting again, a 1 SCU crate can't be split, `parts` stays as API for a later editor. No menus on the overlay, and two clicks at the lift beat a dialog. **Merge rules:** one destination, commodity and rack, not delivered; the sum a crate size and not above the contract's max crate size (the kiosk never delivers larger, D23); all crates from one contract item, because an item's SCU is contract data and must not move between items. **Missions follow:** the contract item that holds the crates (the first in mission order) takes the new crate list as an override, largest first (`MissionItem.WithCrateList`); equal to the derived mix it is dropped (D23 addendum). The `SavedPlan` constructor checks the crate multiset as before; a failure there is a bug, not a player error. **Order in the plan:** the parts take the split crate's index, the merged crate the first merged index, so legend and placements keep their order and split then merge gives the original crates. **Errors like D24:** caller errors stay `ArgumentException` (another ship, a crate not in the plan or named twice, delivered crates, fewer than two crates to merge); refusals are a `PlanException` with the reason. `SplitProblem` and `MergeProblem` return that reason or null: one check for the button and the operation (D25). **Overlay:** two glyph buttons in the header left of the pencil, Split (Segoe MDL2 Cut) and Merge (Link), not focusable, hidden while locked. Enabled by the selection: split for exactly one crate Core can split, merge for two or more Core can merge; disabled they fade, and the tool tip says why (`ToolTipService.ShowOnDisabled`). After the operation the new crates stay selected, so "split, split again" and "merge back" need no new pick. A refusal goes to the notice line ("Split refused: …"). Saved through `ShowPlan` and `PlanSaver` like every change. Precision in the planning phase, ratified by approval.
- **Counter-argument:** The default split can differ from the kiosk: 8 → 4+2+2 takes two steps (8 → 4+4, then 4 → 2+2). A merge needs the crates side by side in the right shape, so sometimes a drag comes first. Crates from two equal contract rows can't be merged into one. A typed override in an unsorted order comes back sorted after a split or merge. An editor left open doesn't see a split or merge until it is opened again. The selection is no longer pure view state (D25 addendum). Two more buttons narrow the header: at the minimum width the ship name is cut short.
- **Consequence:** At the lift the plan follows the kiosk's crates in a few clicks, and the editor shows the overridden item in italics. Not part of this: a split dialog with a choice of parts, merging across racks, merging with moving (not adjacent → drag first), detecting the kiosk's mix, undo.

## D28 – Blur means a text halo, not a backdrop blur

- **Context:** Phase 4 makes the overlay's look configurable. "Blur" on the wish list can mean blurring what lies behind the window (frosted glass) or a soft outline around text and glyphs. The overlay stands over very different scenes, bright at Orison, dark at Lorville, and right next to the cargo lift and the kiosk the player has to see.
- **Decision:** Blur is a **halo around text and glyphs** (legend, rack numbers, header and tabs, buttons), its colour and strength set per section. No backdrop blur behind the window: it would blur the lift and the kiosk under the overlay, the very things the player is looking at. Readability over bright and dark scenes comes from the halo, background transparency and frames. Precision in the planning phase, ratified by approval.
- **Counter-argument:** A frosted backdrop reads well over any scene without tuning each section. A halo per text element may cost render time in the software-rendered layered window (D2), one effect per element instead of one per window. A halo doesn't help a crate fill over a background of the same hue.
- **Consequence:** Backdrop blur stays in the backlog as a spike (DWM backdrop vs. `AllowsTransparency`; whether the two work together is open). The outlined rack numbers (D15) become one case of the halo.

## D29 – Stop colours stay fixed (Okabe-Ito)

- **Context:** Phase 4 lets players tune colours, fonts and transparency. The stop colours (D15: Okabe-Ito without black, plus white) are what the player matches between the legend and the plate.
- **Decision:** Stop colours are **not configurable**. Okabe-Ito was chosen to stay distinguishable with the common colour vision deficiencies; a free palette, or a shared theme, could lose that without anyone noticing. Readability over bright or dark scenes is tuned with frames, transparency and halo (D28), not with the hues. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Some players want stronger or different colours, and a player with a rarer deficiency may be better served by another palette than Okabe-Ito. A fixed colour over a scene of the same hue (orange over Lorville) can still read badly.
- **Consequence:** `MissionPalette` stays as it is. Alternative palettes are backlog, and only ones checked for colour vision deficiency.

## D30 – Settings apply on change, reset per section

- **Context:** The settings window (T4.2) needs a commit model: OK/Cancel as in classic dialogs, or every change taking effect at once. Window position and size already save on change (D13, T3.4).
- **Decision:** Every change **applies to the overlay at once** and is saved like the window bounds (debounced, atomic, D13); no OK, Cancel or Apply. Each section has "Reset to defaults". There is no intermediate state between what the settings window shows and what the overlay uses, and the player tunes readability while looking at the game. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Without Cancel, a failed experiment is undone by hand or by resetting the whole section; a dialog with Cancel would keep a snapshot. Dragging a slider changes the overlay many times per second; the debounce limits the writes, not the redraws.
- **Consequence:** No snapshot, no undo in the settings window; the per-section reset is the way back. Hotkeys (T4.4) follow the same rule: a new combination is registered at once.

## D31 – Settings schema 2: appearance as data, theme as DynamicResources

- **Context:** Phase 4 makes the overlay's look configurable (D28–D30). Each value needs a place in settings.json and a way into the views that the settings window (T4.2) can change while the overlay is open. Without a file the overlay must look exactly as before.
- **Decision:** settings.json **schema 2** adds `appearance` with `window`, `header`, `legend`, `crates`, `buttons` (docs/settings-format.md); `overlay` and `hotkeys` are unchanged, legend visibility and position come with T4.3 as an optional field. Schema 1 is a subset: it loads as is with the default look and is written as 2 on the next save, not on loading (D13: the file stays as the player left it). The defaults are the old literals, guarded by a test; the legend's font size defaults to `null` = the Windows message font size, because that is what the legend used (11 on the development machine, not 12). **Transparency is the alpha of a colour** (`#AARRGGBB`), no separate opacity; the crates' colours are fixed (D29), so their fill and edge alpha are numbers 0–255. Unknown keys and wrong types keep the strict rule (whole file → defaults + notice, D13); **a number out of range is clamped, a colour that isn't one takes its default**, both with a notice line, and the rest applies (`AppearanceRules`, WPF-free). Backgrounds that take clicks keep alpha ≥ 1 (a layered window passes clicks on alpha 0). **Halo** per section: `enabled`, `color`, `size`; text gets a frozen, shared `DropShadowEffect` without offset (soft, D28), the rack numbers keep their sharp outline with the halo's colour and width. The button frame is the glyph buttons'; "Open editor" keeps its outline in the legend colour. **Theme:** `ThemeResources.Apply` fills `Application.Resources` from the settings at startup, keys `<Section><Part><Kind>` (`ThemeResources.Keys`); the views bind with `DynamicResource`, the ship view through dependency properties with `AffectsRender`. A halo that is off removes its key: assigning null through the indexer makes a DynamicResource fall back to the property's default instead of delivering null (spike), and every property bound to such a key defaults to null. The model is positional records with default parameters: in .NET 10 the source generator sets omitted init properties to null/0 instead of their initializers (spike; fixed in .NET 11 per the docs). A missing or null section or halo means its defaults. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Alpha in hex (`A0` = 63 %) is hard to edit by hand; a percentage field would read better. One typo in a key name still resets everything, hotkeys included once the overlay moves. `size` means blur radius for text and stroke width for rack numbers. Defaults live in code, not in App.xaml, so the XAML designer shows no theme colours. Inside a halo object missing keys take the generic halo defaults, so a crates halo written as `{ "size": 5 }` is off. A `DropShadowEffect` per text element costs render time in the software-rendered layered window (D2); default off.
- **Consequence:** T4.2 calls `Apply` again on every change and resets a section to its `Default`. `MissionPalette` keeps only fixed colours; the legend swatches keep their own alpha. The rack number font size comes with T4.6 as `crates.rackNumberFontSize`, legend visibility and position with T4.3, both without a schema bump. An older app can't read a schema 2 file.

## D32 – Rack numbers in screen size

- **Context:** The rack numbers grew with the zoom and the window: `max(12, 0.9 × scale)`, scale = fit × zoom. A font size setting (`crates.rackNumberFontSize`, D31) would have meant a different size at every zoom, and the number "breathed" while orbiting, because the fit follows the camera (D15). D21's backlog said numbers and lines grow; the lines didn't: `ViewTransform` maps every point before drawing, no `RenderTransform`, so pens were in screen pixels already (frame and rack edges 1, free cells and crate edges 0.5, red, cyan and selection 2.5, the number outline the halo size).
- **Decision:** The number has a fixed screen size, `crates.rackNumberFontSize`, optional, no schema bump, default 27 (the old size at zoom 1 in the default overlay with the sample plan, guarded by a test), range 8–48 of its own (the legend's 8–32 would leave the default near the top). Where the number would be taller than the shortest rack side on screen (`RackNumberSize`: shortest edge of all racks in cells × scale; Hull A 2) it shrinks with the racks, down to 12 as before; below that numbers overlap. A setting below 12 is kept. Line widths are unchanged. Hit test and drop target are untouched: the size only enters `OnRender`. Precision in the planning phase, ratified by approval.
- **Counter-argument:** The setting is a maximum, not a fixed size: in a small overlay at 0.5× the numbers still shrink. The rule is a heuristic, how tall a rack side appears depends on the camera, and in the default overlay at 0.5× the margin is small (cap 30 against 27). Hiding numbers below a threshold would be simpler to read but would take the rack number away in the small overview, where the player needs it at the spindle (D9); letting them overlap at any size would make neighbouring numbers cover each other.
- **Consequence:** The number no longer changes while orbiting at normal sizes. The settings window (T4.2) gets the font size in its Crates section. A ship with thin racks (one cell) gets smaller numbers sooner.

## D33 – Legend position and visibility

- **Context:** The legend stood below the ship view across the full width, its lines left-aligned. Next to the kiosk and depending on the overlay's shape it fits better on top or below, left, centred or right; a player who knows the colours wants the stop lines gone. The settings window (T4.2) will switch both while the overlay is open.
- **Decision:** settings.json gets a top-level `legend` with `visible` (default `true`) and `position` (default `"bottom-left"`), optional, no schema bump (D31); top level because it is layout, not look, and "Reset to defaults" per section (D30) must not move the legend with its colours. `position` is one of six names (`top|bottom`-`left|center|right`, lower case), stored as a string and checked by `AppearanceRules` like a colour: an unknown name takes `bottom-left` with a short notice ("edge-alignment, e.g. bottom-right"; the six names would be three amber lines in the default overlay), instead of an enum converter that would make the whole file invalid (D13); wrong types and unknown keys stay strict. `LegendPosition` (edge + alignment) parses it. **Left/centre/right moves a block as wide as its lines**, inside left-aligned so the swatches stand in one column; the hidden hint reserve (D16) counts towards its width and height, so ticking moves neither the block nor the ship view in any position. **Top** is header → notices → block → view; notices always run full width at the outer edge (very bottom, or right under the header), outside the block, so a notice coming and going doesn't push the block sideways. `visible: false` collapses only the stop lines; empty state, violations, hints with their reserve, the palette line and notices stay. Dock, alignment and visibility are style triggers bound to `OverlayViewModel.IsLegendVisible` and `LegendPosition`, not DynamicResources: structure, not theme values, testable without a window; changing `DockPanel.Dock` re-measures the parent (`OnDockChanged`). The legend drag (D25) needs no change: the view captures the mouse and works in its own coordinates, above or below it alike. Checked offscreen with `RenderTargetBitmap`: bottom-left is pixel-identical to before, and ticking every stop moves the view in none of the twelve layouts, switched live on one window. Precision in the planning phase, ratified by approval.
- **Counter-argument:** Two `legend` keys on two levels invite `appearance.legend.position`, an unknown key that resets the whole file. The six names live in our own code instead of the serializer. A block as wide as its lines has a ragged right edge at `right`, and a violation after a move changes its width, so at centre or right it shifts sideways (editing, not ticking, accepted like D20). Notices stay left-aligned when the legend stands right. On top, a notice that appears ("Move refused") pushes the ship view down while the player looks at the crate just dropped; below, the view shrinks too but its top edge stays. A fixed one-line notice reserve like the hints would fix that, only once it bothers in the game.
- **Consequence:** With `visible: false` dragging a whole stop from the legend (D25) is gone with the lines; a stop is then moved through the crate selection (T3.14b), and settings-format.md says so next to "hides only the stop lines". T4.2 sets the two view model properties besides calling `ThemeResources.Apply`. Unchanged and the same in every position: the view clips its drawing (`ClipToBounds`) but the hit test doesn't, so a drop over the legend can hit a rack part zoomed out of sight (backlog).
- **Addendum (T5.1), notices fixed at the bottom left:** Notices no longer follow `legend.position`. They are a child of the overlay's outer DockPanel of their own, docked at the bottom before the legend area, so they are always the bottom line, full width and left-aligned; a bottom legend stands above them, a top legend under the header. Nothing gives way sideways: at `bottom-*` the layout is the same as before, at `top-*` a notice coming and going no longer pushes the ship view down while the player looks at the crate just dropped, the view's top edge stays. Reason: the ContractTracker import (T5.3–T5.5) brings more notices. Replaces "notices … right under the header" above. Precision in the planning phase, ratified by approval. **Counter-argument:** At `top-*` a notice stands far from the legend it used to belong to, and the ship view still shrinks when one appears, now from below; a fixed one-line reserve would stop that too, still only once it bothers in the game. Overlaying the notices on the ship view's bottom-left corner would move nothing, but could cover crates and rack numbers.

## D34 – Settings window: one settings session, system look, gear next to the padlock

- **Context:** Editing settings.json by hand puts haulers off (D17), and readability is tuned in the game, not in a text editor (D30). T4.1–T4.6 built the model, its checks and the DynamicResources. `OverlayBoundsSaver` kept its own copy of `AppSettings`: a look saved from a settings window would have been overwritten with the old look by the next move of the overlay.
- **Decision:** **`SettingsSession` is the one owner of the current `AppSettings`.** Its constructor applies the loaded settings at startup without writing (D31); `ChangeLook` from the settings window runs the same `AppearanceRules.Normalize` as loading, applies through the same method (`ThemeResources.Apply` plus the view model's legend layout) and saves debounced by 500 ms; `ChangeBounds` from `OverlayBoundsSaver` (still debounced there) saves at once, a pending look with it; `Flush` on the overlay's `Closed` writes what is pending. A correction from the window keeps its notice after saving, so a slider with a wrong limit shows at once instead of after a restart. **`SettingsViewModel`** is WPF-free and returns appearance and legend layout, not a whole `AppSettings`: its copy would hold stale bounds. Building blocks `ColourField` (hex `#RRGGBB`, `#` optional, plus an alpha slider 0–255 with a percent label and a swatch on a checkerboard; eight digits are invalid so field and slider can't disagree; an invalid hex tints the field, applies nothing and shows no notice) and `HaloEditor` (switch, colour, size), reused by T4.2b. Slider limits are `AppearanceRules`' constants via `x:Static`; clickable backgrounds start at alpha 1. "Use Windows text size" is `fontSize: null`; unticked, the slider starts at the Windows size clamped into 8–32. Reset per section to its `Default`, applied once; legend layout is a section of its own (D33). **The window has the system look**, not the theme, so nobody themes away the tool to undo the theme. Like the editor (D19): one instance, owned by the overlay, topmost, `ShowActivated=False`, hidden with the overlay and while auto-locked (`OverlayViewModel.AreToolWindowsHidden`, shared with the editor through `OverlayWindow.HideWithOverlay`); Esc and X close it; it opens next to the overlay (`SettingsWindowPlacement`), the position is not saved. **The gear sits right of the pencil, next to the padlock:** window controls right, plan controls left; hidden while locked like every header button. **Way out of an invisible theme:** the gear keeps alpha ≥ 1 and takes the hover, its system tool tip "Settings" shows over an invisible glyph; the README says where to hover, or to delete `appearance` from settings.json. No start switch, no contrast floor. Hotkeys get their section with T4.4. Split into T4.2a (session, gear, window, sections Window, Legend, Legend layout) and T4.2b (Header, Crates, Buttons). Precision in the planning phase, ratified by approval.
- **Counter-argument:** The hex field applies on every keystroke (`UpdateSourceTrigger=PropertyChanged`), so retyping `#E6E6E6` as `#FF0000` flashes `#FF6E6E` and `#FF006E` through the overlay; LostFocus plus Enter would be calmer, and is a one-line change in the binding if a hauler reports the flicker. ## D35 – Hotkeys recorded in the settings window; refused, not saved, when taken

- **Context:** Hotkeys were set in settings.json only (D17); a typo made the whole file invalid. T4.4 adds a Hotkeys section to the settings window (D34): press the keys instead of typing them, with the same rules and still no defaults.
- **Decision:** **Recording reads key events of our own focused window** (`KeyDown`, `Key.System` → `SystemKey` while Alt is held, `Keyboard.Modifiers`, `KeyInterop.VirtualKeyFromKey`; `RecordedKey`): no hook (D17). A modifier alone waits for the key after it; Esc cancels without closing the window; losing the focus, hiding (auto-lock) or closing the window cancels too. **While recording, our hotkeys are suspended** (`HotkeyService.Suspend`/`Resume`): Windows turns a registered combination into `WM_HOTKEY`, so its keys would never reach the window, and pressing the lock's keys would switch the lock. **Same rules as typed text:** `HotkeyParser.TryCreate` shares its checks and reasons with `TryParse` (Ctrl, Alt or Win required, F12 reserved, only keys from the table); a refused combination shows its reason at the button and recording goes on. **A combination that is taken is refused and not saved:** the other action's combination by name ("already used for Lock / unlock", a pure check in `HotkeysViewModel`), another program's by `RegisterHotKey` failing (`HotkeyService.TrySet` puts the old hotkey back). Only a registered hotkey is saved (`SettingsSession.ChangeHotkey`, debounced like the look), as canonical text; **Clear writes `null`**, so the entry stays visible, and `null` and missing read the same. The hint says Ctrl, Alt or Win is required and that Win combinations may be taken by Windows itself. No "Reset to defaults" in this section: the default is no hotkey (D17), which is Clear. `HotkeyEditor` and `HotkeysViewModel` are WPF-free; the section has its own data context, `SettingsViewModel` stays the look. Precision in the planning phase, ratified by approval.
- **Counter-argument:** T3.7 saved a taken combination and reported it in the overlay; refusing it means a combination another program frees later has to be set again. A combination another program has registered probably never reaches the window, so recording it does nothing and only the hint explains why; the "in use by another program" path is mainly for programs that take it between pressing and registering. Win combinations are often taken by the shell. While recording, our hotkeys don't work. Two view model classes for two actions; one would be shorter, but the duplicate check needs both. Alt+Space may still open the window's system menu.
- **Consequence:** settings.json need not be edited for anything in the settings window any more. A hotkey invalid in the file shows in the overlay's notice line and at its button; Clear or a new combination removes it. The startup notice for a taken combination points at the settings window.

## D36 – Tool windows in WPF's Fluent theme, per window, with a fixed teal accent

- **Context:** Settings window, mission editor and colour picker had the system look (D34) and glared over the dark game. Wanted: three fixed modes light, dark and system (follows Windows live); the overlay keeps `appearance` (D34). Two ways: **F**, WPF's Fluent theme through `Window.ThemeMode` (.NET 9+, experimental, `WPF0001`), or **E**, own templates for about 14 controls with a palette record, a `WM_SETTINGCHANGE` watcher and the DWM title bar. (4) The settings window shows a mixed look: own styles without `BasedOn` fall back to Aero2. (6) Markings follow the mode through Fluent's `SystemFillColorCritical/Caution(+Background)Brush`. (7) Martin's look next to the overlay: F.
- **Decision:** **Way F with a fixed teal accent.** `ToolWindowThemer.Apply(window, ToolWindowTheme)` sets `ThemeMode` on each tool window, never on the application, and the accent into the window's resources; `ToolWindowTheme` (System, Light, Dark; `default` = System) is WPF-free. Fluent follows Windows in `System` mode by itself and switches to its own high-contrast dictionary, so there is no watcher, no DWM call and no own template. **Pattern for own styles**, found in the sample: `Apply` runs before `InitializeComponent`, and sets `ThemeMode` before it touches `Resources`, because the setter loads Fluent at once only while the window has no resources yet and otherwise waits for the window handle, after the XAML. Own styles are `BasedOn` Fluent's and stand **one level below the window** (the root panel's resources): a style keyed `{x:Type Slider}` that looks up `{x:Type Slider}` skips its own dictionary, the merged Fluent one included, and ends up with no base at all. Fixes: `HueSliderStyle` (App.xaml, keyed) draws the spectrum as the track with Fluent's `SliderThumbStyle`; disabled sliders and text boxes fade to opacity 0.4 like the overlay's icon buttons; the popup uses `FlyoutBackground`/`FlyoutBorderBrush`. Precision in the planning phase, ratified by approval.

The rule "own styles one level below the window" is not obvious: a style put into `Window.Resources` silently falls back to Aero2. The look is Windows 11, not sci-fi; Fluent's controls are larger, so the settings window grows. The tinted invalid row is gone. File dialogs and message boxes stay in the system look.

## D38 – ContractTracker database: what we read and how it behaves

- **Context:** Before the reader (T5.3) and the sync (T5.4), T5.2 looked at the database of ContractTracker V2 (closed source) with the `sqlite3` CLI, on copies only: the schema first, then a lifecycle protocol where Martin used ContractTracker 2.2.0.0 and every step was read as a consistent read-only snapshot (`.backup`) plus a count of the commit frames in the write-ahead log. Licence question asked of the author in the Nexus Discord on 2026-10-20 09:26; no answer yet. If the answer is no, the schema file goes, this entry stays.
- **Decision:** The database is found at **one fixed path**, `%APPDATA%\SCContractTracker\contracts.db`. The **fingerprint** is the list of (table, column, declared type) the reader reads, in the schema file: each one must exist with its type, anything else (more columns, more tables) is ignored. There is **no version signal** to check instead: `user_version` is 0 and there is no migrations table. Precision in the planning phase, ratified by approval.

## D39 – ContractTracker prefills the editor; we parse the raw text

- **Context:** D37 planned a sync from ContractTracker into the plan (T5.4). The D38 addendum revised the premise of D37: a capture is incomplete in ContractTracker's rows, but its raw OCR text holds every destination; ContractTracker's parsing loses them.
- **Decision:** ContractTracker becomes a **prefill for the editor, not a sync source**: the reader yields import candidates the player reviews before they reach the plan. We **parse the raw text ourselves**; ContractTracker's child rows are the fallback. A candidate is keyed by its **ContractTracker ids**; new ones are read above a **watermark** (the highest reviewed id, accepted or discarded) that belongs to the plan; no content key. Reason from the game: a silent sync with missing destinations shows up at the freight elevator, and a plan you distrust is worse than none. **Revision of D37, ratified by approval.**
- **Counter-argument:** One more click and one review per contract; D37's idea of contracts showing up in the overlay without a step in between is dead. That is the deliberate price. Parsing ourselves means **we** follow layout changes in the game, not ContractTracker.
- **Consequence:** T5.3 is reader plus raw-text parser and yields candidates; T5.4 is review in the editor plus incremental placement, without reset detection, "gone = fulfilled", multiset and content debounce; T5.5 switches a notice, not a sync. D38's consequences for T5.4 (multiset, reset detection) are superseded; "diff, don't react" stays and now means: a file event yields a notice only if rows above the watermark exist.
- **Addendum (same day, nothing built yet): review moves from the editor to the legend.** Revision of D39's review location, ratified by approval.
  - **Context:** In the game a hauler presses F3 at the terminal and looks at the overlay; the editor is opened only when something is wrong. A mandatory review in the editor would cost a window and a click per contract at the terminal, too cumbersome to be used.
  - **Decision:** Candidates go **straight into the plan**; the watermark rises when a candidate is applied. Whatever is uncertain is **marked in the legend** at its stop: crate size assumed ("4 SCU?"), destinations incomplete ("⚠ 1 of 3 destinations"), fallback to ContractTracker's child rows. **Every capture becomes a mission of its own, nothing is replaced:** a capture with the same commodity and overlapping destinations as a mission without ticks is marked "⚠ duplicate?", with no notice; the marking disappears with the first tick on either. The player decides at the elevator: two real contracts → ignore the marking; a retry after an OCR error → delete the wrong mission in the editor. Reason from the game: the plan must rather know too many crates than too few. A crate too many is an empty cell at the elevator, one glance; a crate too few has no place, and the hauler improvises exactly where the tool should take the load off. Replacing is silent data loss, adding is visible and reversible. **Deleted in ContractTracker:** all crates of the mission ticked → the mission leaves the plan; otherwise a notice, the plan stays.
  - **Unchanged:** the core of D39: our own raw-text parser with the child rows as fallback, candidates keyed by ContractTracker ids above a watermark that belongs to the plan, no content identity across captures; the duplicate check only marks, it never merges.
  - **Counter-argument:** A phantom destination sits in the plan until the player removes it. A retry leaves a duplicate that takes rack space until it is deleted: in a full 64 SCU Hull A that can be the rack the next contract needs. Both are the price of zero clicks, made visible by the markings.
  - **Consequence:** T5.4 becomes auto-apply with markings plus incremental placement; applied missions keep their ContractTracker ids in the plan, needed for the deletion notice; removing a mission (deleted in ContractTracker, deleted in the editor) moves no other crate. "Sync from ContractTracker" in the editor stays as the manual way. T5.5 switches auto-sync again. T5.3 is unchanged; its hints feed the legend instead of a review. Superseded in D39: review before the plan, the watermark as "highest reviewed id" (now: highest applied), the one-click-per-contract counter-argument. "Gone = fulfilled" returns only in the narrow form above (deleted and fully ticked).

## D40 – One normalisation, in the parser

- **Context:** T5.4 marks a capture "⚠ duplicate?" when it has the same commodity and overlapping destinations as a mission without ticks. That only works if names from different captures of one contract come out equal. The raw texts of T5.2 show why they don't by themselves: destination lines end in " at"/" above" or are cut off mid-name ("to Thundering", "to Thundering Express"), "LS" stands for "L5", and ContractTracker's destination rows carry tails of prose. The anchors of the contract text ("DETAILS", "ACCEPT OFFER") are matched tolerantly (O/0, I/L/1 alike) and are optional: a capture from the "Accepted" tab, not observed, has no "ACCEPT OFFER". Precision in the planning phase, ratified by approval.
- **Counter-argument:** Normalising is lossy: the raw form is gone, and a wrong correction can't be seen in the plan (the raw text stays in ContractTracker and comes out with `contracts --raw`). Missions typed in the editor don't pass through the parser, so a duplicate between a capture and a typed mission is found only if the names happen to match. Cutting at " at " breaks a station whose name contains " at ". When no full name is in the text, a cut-off destination stays a fragment ("Thundering Express"), and a later complete capture of the same station does not match it.
- **Consequence:** The normalised name is not only compared, it is the stop in the plan and the label in the overlay; normalising only in the comparison would have put "Thundering" and "Thundering Express" into two racks. Candidates carry normalised names; T5.4 needs no key of its own. A new OCR error class is fixed in one place and covered by a fixture from a bug report (`CargoPlan.Cli contracts <db> --raw`).
- **Addendum (T5.3, same day): completion by character prefix, from the drop-off list only.** Precision in the planning phase, ratified by approval.
  - **Context:** A capture from the Accepted tab (ids 37/38) broke a delivery line mid-word: "to Thunde", with "oss Station" two lines further down, and cut "to High Course" off. Completion by word prefix missed both. The Accepted view ends in TRACK/ABANDON, not ACCEPT OFFER; DETAILS is in both views (contracttracker-schema.md, "Raw text layouts").
  - **Decision:** A destination without a name end is completed in two steps. First from the **drop-off list** only, by **character prefix**, and only if **exactly one** entry starts with it. Then a fragment left over takes the one longer destination of the same capture that starts with it (ids 28/29 have no list). Otherwise the fragment stays. The pick-up list and "freight elevator at …" in the prose no longer complete anything.
  - **Counter-argument:** A character prefix matches more than a word prefix: a fragment of one letter takes the only list entry starting with it, right or wrong. Two rules instead of one. Without a drop-off list, a mid-word fragment ("Thunde") stays unless another delivery of the capture completes it.
  - **Consequence:** "Thunde" → "Thundering Express Station", "High Course" → "High Course Station"; two list entries with the same start keep the fragment, and the overlay shows the fragment as the destination. A pickup that shares a destination's prefix can't be taken for it.

## D41 – Incremental placement: new missions into free cells, existing crates fixed

- **Context:** Contracts are accepted one by one (F3 per contract, D39 addendum); planning again lays out every crate anew and clears ticks (T3.8b). Spike T5.4: `LoadPlanner.Plan` always starts from empty racks and chooses racks globally (a DP over all stops), so a fifth stop moves the second into rack 1. `CrateLayout.Place` already lays crates into a rack's free cells around fixed ones, with fill order and support rule (used by `MoveStop`). From the game (Martin): at the pickup elevator the player selects whole missions to load; delivered crates are off the ship; a crate with another on top along the stack axis can't be taken away; ContractTracker does nothing on Abandon.
- **Options:** (a) `PlaceInto` in Core: append the new crates, existing ones untouched by construction; rack choice: first the racks of a stop with the same destination (one handover, D42), then the first empty rack in rack order, then the first rack with room, then crate by crate in rack order; layout by `CrateLayout.Place`. (b) Re-plan with frozen crates as a constraint: the DP cuts one crate line into contiguous SCU segments per rack; frozen crates break that (partial racks, free space is a shape, not a number), which makes it a second planner, and it gains nothing where fixed crates block the shape. (c) Full re-plan: ruled out (T3.8b, loses positions and ticks).
- **Decision:** (a). **Cells of delivered crates are free** (D24 addendum). **New crates never lie on top of an earlier stop's crate along the stack axis,** enforced by `CrateLayout.Place` (D24 addendum, T5.4a). ContractTracker missions bring their order from the contract text, first appearance as in the editor (D19); a contract that says "ANY ORDER" (Martin) leaves the route to the player in the editor. A new mission joins the route at its end, so its crates rest on nothing of another destination: that follows from the rule, it is no rule of its own. **Doesn't fit → the mission enters the plan without crates**, the legend says "⚠ doesn't fit (16 SCU, 8 free) – tick to drop" (or names the shape), and the watermark rises; ticking drops the mission from the plan, deleting it in the editor does too. No partial placement: the elevator hands out whole missions, half a mission is no action in the game. A notice alone would lose the contract once the watermark passes it, or repeat forever, since ContractTracker keeps an abandoned contract. Spike T5.4, ratified by approval.
- **Counter-argument:** Greedy rack choice fragments: four stops of 12 SCU (max 4) leave 4 SCU free in every rack, 16 SCU in all, yet no 8 SCU crate fits; a full re-plan fits a 16 SCU mission in 8 SCU crates by moving stops into shared racks. "First stop in rack 1" erodes with every capture, and shared/spans hints become more common. A second rack-choice rule lives next to `Partition`. An unplaced mission is a new plan state. **The tick gets a second meaning:** on a placed stop it says "delivered", on an unplaced mission "abandoned, out of the plan"; without "tick to drop" in the legend the player doesn't find the gesture, or ticks out of habit and loses the mission. Ticking back stops being an undo once a delivered stop's cells are reused.
- **Consequence:** Needs the mission identity of D42 first (plan schema 3), which also carries the unplaced state; dropping an unplaced mission is per mission, not per stop. T5.4a (stacking rule) comes before T5.4. When an unplaced mission is placed after space frees up is part of T5.4's planning. Re-planning in the editor stays the explicit way out when nothing is loaded yet or the route changes.

## D42 – Mission identity under the stop (plan schema 3)

- **Context:** T5.4 adds every ContractTracker capture as a mission of its own (D39 addendum); a capture has one or more destinations. The Core's unit is the destination: one `MissionStop` per destination (planner, mission file), ticks per stop (D16), crates without a mission. Removing a mission, marking duplicates, keeping ContractTracker ids and an unplaced mission (D41) need to know which crates belong to which mission. From the game (Martin): the destination elevator takes crates of several missions to the same destination in one handover; the kiosk splits crates within a mission; crates of two missions come up the pickup elevator together, told apart by colour at most.
- **Options:** (a) A mission id on every item and crate; stops stay one per destination; the plan keeps a list of missions (id, ContractTracker ids, hints, unplaced). (b) Stop = mission + destination: a destination may occur twice, in planner, mission file and legend. (c) No identity, removal by matching contents: ruled out, equal crates of two missions can't be told apart (D38: no content key).
- **Decision:** (a). Reason from the game: at the elevator the destination is the unit (one handover, so rack, tick and hints stay per destination); the contract is the unit of the crate mix, of duplicates and of removal. (b) would split one handover over two stops and racks. Spike T5.4, ratified by approval.
- **Counter-argument:** `Crate`, the derived placements, the plan file and the editor all grow by a field, and every crate carries an id the player rarely sees. The editor has no missions today: rows entered by hand need a mission too. Ticks stay per stop, so a mission abandoned at a destination another mission still goes to is removed in the editor, not ticked.
- **Consequence:** Plan schema 3 (`missions` with id, `crates` with `mission`); schema 2 is migrated on reading, one mission per stop. Merge refuses crates of different missions, split keeps the mission (D27). How the editor shows and deletes missions is part of T5.4's planning.
